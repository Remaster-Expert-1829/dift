# Security, Privacy, and Threat Model

> Status: Approved  
> Trust decision: ADR-003

## Security objectives

1. Authenticate the paired device on every normal connection.
2. Protect file content and protocol metadata in transit against passive and active network attackers.
3. Prevent network input from escaping destination/store roots or exhausting unbounded resources.
4. Detect corrupted or substituted chunks/files before finalization.
5. Protect local identity keys and ephemeral session capabilities.
6. Make the plaintext-at-rest limitation explicit.

## Trust model

The operator trusts both paired devices, their operating systems, and the receiving user with plaintext. The local network is untrusted. Other LAN devices may scan ports, send malformed traffic, intercept connections, or attempt denial of service. Paired devices are trusted for identity but their input is still validated because software compromise or bugs remain possible.

V1 does not protect against:

- a compromised local OS, administrator/root user, or malicious receiving operator;
- theft of plaintext final files or chunk store from an unencrypted disk;
- traffic analysis such as connection timing/volume;
- user failure to compare the pairing SAS;
- denial of network reachability;
- malicious source content consumed later by another application.

## Assets

- device private key and public identity;
- trusted-peer pins and revocation state;
- file content and relative filenames;
- manifests and content hashes;
- session capabilities and transfer IDs;
- destination integrity and existing files;
- chunk-store/SQLite integrity and availability;
- logs/reports that may reveal activity or paths.

## Threat actors

- unpaired LAN peer;
- active man-in-the-middle during pairing or normal transfer;
- paired but malfunctioning/compromised peer;
- unprivileged local process/user;
- accidental operator/configuration error;
- corrupted disk or externally modified state.

## Trust boundaries

```text
CLI/config → validated application state
source filesystem → sender pipeline
TLS socket → protocol decoder → domain messages
encoded chunk → bounded decompressor → hash verifier
manifest path → contained destination resolver
application → SQLite/chunk store → final filesystem
telemetry event → redaction/filter → logs/reports
```

## Authentication and pairing

- All normal control/data connections require TLS 1.3 mutual authentication against pinned SPKI fingerprints.
- Pairing uses the restricted ALPN and accepts provisional certificates only within that state machine.
- The SAS is derived from TLS exporter material and both identities/nonces, not sent as a comparable plaintext value.
- Both users confirm. Default is reject. One explicit listener accepts one attempt; retry requires operator action.
- Peer ID and TLS certificate identity must match message fields.
- Certificate/key renewal with a new public key requires re-pairing. Same-key certificate renewal policy is accepted only if certificate validity/key-usage checks pass and the SPKI pin is unchanged.
- Revocation is local and immediate for new/resumed connections. Active connections for a just-revoked peer SHOULD be closed.

## Secrets

| Secret | Storage | Handling |
|---|---|---|
| Device private key | Restrictive local file, never SQLite/log/output | Generated by OS CSPRNG/library; loaded only into TLS context; zero/release library buffers per API. |
| Session capability | Memory on sender/receiver control epoch | 32 random bytes; constant-time compare; rotate on resume/control replacement; never persist/log. |
| TLS session keys | TLS library memory | Library-managed; disable insecure protocol/cipher fallback and key logging in release builds. |

File content is sensitive data but not a protocol secret after the trusted receiver stores it. Core dumps and debug tooling can expose it; release operations SHOULD disable or restrict core dumps on sensitive systems.

## TLS policy

- Minimum and maximum protocol for v1: TLS 1.3.
- Use library defaults restricted to supported authenticated TLS 1.3 cipher suites; do not hardcode one suite without platform evidence.
- Certificate public key algorithm and minimum strength are selected in security build policy before release (`TBD-SEC-KEY-001`); weak/deprecated keys are rejected.
- Compression at TLS level is disabled; application compression occurs before TLS.
- Renegotiation/legacy protocols are unavailable under TLS 1.3.
- 0-RTT data is disabled because transfer/control messages are replay-sensitive.
- TLS errors are not retried as congestion failures.

## Input validation

### Protocol

- Validate magic/version/channel/type/reserved bits and lengths before allocation.
- Intersect negotiated limits; never accept a peer-advertised value above local absolute ceilings.
- Use checked arithmetic for lengths, offsets, counts, and buffer calculations.
- Enforce message order and one-session binding.
- Treat CBOR duplicate keys, invalid UTF-8, indefinite lengths, floats, tags, and non-deterministic manifest encoding as invalid where forbidden.

### Compression

- Output buffer limit equals exact declared plaintext length and global maximum.
- Reject trailing/unconsumed compressed bytes if codec APIs expose them.
- Hash after decompression; no codec result is trusted.
- Decompression runs in bounded worker capacity to prevent CPU exhaustion.

### Filesystem

- Normalize manifest paths and reject absolute/traversal/control-character inputs.
- Resolve below an opened destination root using file-descriptor-relative operations and no-follow flags where supported.
- Reject symlinks in selected source traversal and destination path components under v1 policy.
- Create staging files exclusively with restrictive permissions.
- Never use a received filename as a format string, shell command, store filename, or SQL fragment.
- Existing destinations are replaced only after verification and explicit approval.

### Resources

Bound handshakes per address/device, sessions, files, chunks, path bytes, manifest bytes, frame bytes, queues, in-flight bytes, connections, retries, decompression work, DB busy wait, temporary disk use, and telemetry backlog. Rate-limit repeated pairing/auth/protocol failures without relying on IP as identity.

## Threats and controls

| Threat | Control | Residual risk / detection |
|---|---|---|
| Pairing MITM | TLS-exporter SAS comparison on both screens | Human may not compare; audit pairing attempts/results. |
| Normal-session MITM | mTLS and SPKI pin | Compromised key; revocation/re-pairing required. |
| Replay on new connection | TLS; fresh connection/session nonce; current in-memory capability; state/idempotency checks; no 0-RTT | Valid paired sender can retry idempotently by design. |
| Unknown device transfer | Pinned-peer requirement plus receiver approval | Paired device compromise remains. |
| Path traversal/symlink race | Strict normalized relative paths, root-relative no-follow filesystem operations, destination reservation | Platform-specific filesystem behavior requires tests. |
| Zip/decompression bomb | Exact decoded-length bound and worker/resource limits | CPU within allowed chunk still consumed; telemetry/rate limits. |
| Memory/socket exhaustion | Limit-first parsing, bounded queues/pools, handshake/session caps | LAN DoS can still consume bounded capacity. |
| Disk exhaustion | Preflight estimate/free reserve, per-session limits, stop ACKing on capacity error, cleanup policy | Other processes may consume disk concurrently. |
| Hash collision/substitution | SHA-256, length checks, whole-file SHA-256, TLS | Cryptographic collision considered negligible; algorithm agility requires future ADR. |
| Store tampering | Startup/periodic verification, quarantine, whole-file verification | Trusted local administrator can tamper/replace application itself. |
| Refcount/GC bug | Recompute from normalized references, leases, conservative deletion, dry-run | May leak storage rather than delete uncertain data. |
| Log disclosure | Structured allowlist/redaction; no contents/keys/capabilities/full roots | Relative filenames may still be sensitive; configurable report storage. |
| Downgrade | TLS 1.3 only, explicit protocol negotiation, manifest binds major | Future version negotiation must preserve rule. |

## Authorization

V1 authorization is device-level plus per-session receiver approval. A paired peer is not automatically allowed to write any path. Receiver selects a destination root and approves offered paths/overwrite intent. There are no users/groups/ACLs. Unattended allow rules are deferred.

## Privacy

The receiver learns filenames, sizes, plaintext chunk hashes, and plaintext contents. Local deduplication reveals equality only within that receiver's store. No data is sent to third parties. Telemetry defaults to hashed/truncated peer IDs and relative-path omission in persistent logs; interactive UI may show paths to the local operator.

## Third-party and supply-chain controls

- Pin reviewed dependency versions/commit hashes through the chosen package strategy.
- Record licenses and include required notices.
- CI scans known vulnerabilities and verifies downloaded artifact checksums/signatures where supported.
- No runtime plugin loading or network dependency download in normal transfer execution.

## Security tests and release blockers

- Pairing MITM/two-connection SAS mismatch simulation.
- Unknown/revoked/changed identity rejection.
- Protocol parser fuzzing and malformed length/CBOR corpus.
- Path traversal, Unicode, symlink-race, and destination-replacement tests.
- Decompression bombs/truncation/trailing-data tests.
- Capability theft/reuse/wrong-session tests.
- Resource-limit and connection-flood tests.
- Log scan proving absence of private keys/capabilities/content.
- Dependency vulnerability review.

`TBD-SEC-KEY-001` and `TBD-LIMITS-001` block a release build, but not isolated domain/storage implementation.
