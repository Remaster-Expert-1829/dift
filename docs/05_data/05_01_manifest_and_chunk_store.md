# Manifest and Chunk Store

> Status: Approved logical model; initial schema version is `1`.  
> Decision: ADR-004

## Storage layout

```text
<state-root>/
├── identity/              private key, certificate, public metadata
├── metadata.sqlite3       transactional metadata
├── chunks/aa/bb/<hash>    verified plaintext chunk blobs
├── chunk-tmp/             same-filesystem temporary chunk writes
├── quarantine/            inconsistent/corrupt store evidence
└── reports/               optional non-secret transfer summaries

<destination-root>/
└── .deltasync-staging/<transfer-id>/...  staged reconstruction
```

Exact configurable roots are operational details. Canonical chunk filenames use the 64-character lowercase SHA-256 hex digest. Fan-out uses the first two and next two hex characters. No network-provided path is concatenated directly into a store path.

## Canonical manifest

The manifest is a deterministic CBOR document using RFC 8949 deterministic encoding. It contains only integer, byte-string, text-string, array, map, and Boolean values; floating point and indefinite-length items are forbidden. Map keys are the exact short text keys defined by the wire contract and are sorted by deterministic CBOR rules.

```text
Manifest {
  schema: 1,
  protocol_major: 1,
  sender_peer_id: 32-byte value,
  created_at_unix_ms: integer,       // informational; included in digest
  chunk_profile: {
    id: text,
    algorithm: "rabin",
    parameters: map                  // exact profile parameters
  },
  files: [
    {
      file_id: unsigned integer,
      relative_path: UTF-8 text,
      logical_size: unsigned integer,
      sha256: 32-byte value,
      chunks: [
        { ordinal, offset, length, sha256 }
      ]
    }
  ]
}
```

Files are sorted by normalized relative-path UTF-8 byte order. `file_id` is then assigned from zero in that order. Chunks are ordered by ordinal/offset. The manifest digest is SHA-256 of the complete deterministic CBOR bytes.

`created_at_unix_ms` prevents two independently created otherwise-identical transfer offers from sharing a manifest digest. Content reuse is based on chunk hashes, not manifest identity. If reproducible identical manifest identity becomes desirable, this field must be removed through a schema/version decision before protocol freeze.

## Path representation

- Manifest paths are relative UTF-8 strings using `/` separators.
- Empty path segments, `.`, `..`, leading `/`, trailing `/`, NUL, control characters, and backslash are rejected.
- Unicode is normalized to NFC before manifest construction. The receiver verifies that normalization.
- Each path is interpreted below the receiver-selected destination root; manifest content cannot select an absolute root.
- Linux v1 treats path bytes case-sensitively but rejects exact normalized duplicates. Cross-platform case policy is deferred.

## SQLite rules

- `PRAGMA foreign_keys = ON` on every connection.
- WAL mode is configured and verified at startup.
- Timestamps are signed 64-bit Unix milliseconds in UTC.
- Boolean values are integer `0/1` with checks.
- SHA-256 values are exactly 32-byte BLOBs in SQLite; CLI/log representation is lowercase hex.
- Enums are uppercase text with `CHECK` constraints so inspection remains readable.
- Application code uses prepared statements only.
- Network/file operations do not occur while a SQLite write transaction is open.

| Column | Type | Constraints / meaning |
|---|---|---|
| `chunk_hash` | BLOB | Primary key, exactly 32 bytes. |
| `plaintext_length` | INTEGER | Positive for non-empty chunks; empty files have no chunk row. |
| `state` | TEXT | `MISSING`, `INSTALLING`, `VERIFIED`, or `QUARANTINED`. |
| `store_relpath` | TEXT | Nullable until verified; unique when present. |

If an existing hash is presented with a different plaintext length, the operation fails with `HASH_METADATA_CONFLICT` and raises an integrity alert.

### DB-005 — `file_chunk_refs`

| Column | Type | Constraints / meaning |
|---|---|---|
| `transfer_id` | BLOB | Part of foreign key/primary key. |
| `file_id` | INTEGER | Part of foreign key/primary key. |
| `ordinal` | INTEGER | Non-negative, part of primary key. |
| `chunk_hash` | BLOB | Not null; foreign key to `chunk_catalog`. |
| `file_offset` | INTEGER | Non-negative. |
| `chunk_length` | INTEGER | Positive; must match catalog length. |

Primary key: `(transfer_id, file_id, ordinal)`. Unique: `(transfer_id, file_id, file_offset)`. Index: `(chunk_hash)`.

Manifest insertion creates `file_chunk_refs` and updates `manifest_ref_count` only for accepted files. Rejected file summaries may remain in `transfer_files` and the retained canonical manifest for audit/result integrity, but they do not acquire chunk references or trigger payload requests. Accepted-file insertion validates contiguity and updates counts in the same transaction. Refcounts are treated as cached integrity-protected data; startup/maintenance can recompute them from this table.

### DB-006 — `session_chunks`

| Column | Type | Constraints / meaning |
|---|---|---|
| `transfer_id` | BLOB | Foreign key with cascade, part of primary key. |
| `chunk_hash` | BLOB | Foreign key to catalog, part of primary key. |
| `state` | TEXT | `NEEDED`, `IN_FLIGHT`, `VERIFIED`, or `FAILED`. |
| `attempt_count` | INTEGER | Non-negative. |

| `verified_at_ms` | INTEGER | Nullable. |

Primary key: `(transfer_id, chunk_hash)`. Index: `(transfer_id, state)`.

This table deduplicates a hash required by several files in the same session and is the authoritative resume progress view.

### DB-007 — `chunk_leases`

| Column | Type | Constraints / meaning |
|---|---|---|
| `lease_id` | BLOB | Primary key, 16 random bytes. |
| `chunk_hash` | BLOB | Foreign key to catalog. |
| `owner_transfer_id` | BLOB | Nullable foreign key. |
| `purpose` | TEXT | `RECONSTRUCT`, `SEND`, `VERIFY`, or `GC`. |
| `process_instance_id` | BLOB | Not null; identifies current process run. |

Index: `(chunk_hash, expires_at_ms)`. Leases are renewed while used. Leases from a prior process instance are expired during startup reconciliation after confirming that process cannot still be active under the single-instance store lock.

## Relational invariants

- Accepted receiver session insertion includes session, files, chunk catalog placeholders, ordered references, and needed/verified session-chunk state in one transaction.
- A `VERIFIED` session chunk requires a `VERIFIED` catalog row and existing canonical blob.
- A completed file requires every referenced catalog chunk verified and a successful whole-file check.
- A completed session requires every accepted file completed.
- Refcount cannot be the sole deletion proof; GC verifies no `file_chunk_refs` and no live lease.
- Terminal session cleanup removes references transactionally before chunks become GC candidates.

## Data dictionary conventions

- Sizes and offsets are unsigned conceptually but stored in signed SQLite integers; values above `INT64_MAX` are rejected.
- Counts are bounded below configured limits and also below `INT64_MAX`.
- Error codes are stable uppercase ASCII identifiers defined in the contract.
- Display names and paths are data, never log-format strings.
- Full local paths are sensitive operational data and are redacted in default logs.
