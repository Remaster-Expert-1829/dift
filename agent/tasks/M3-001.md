## Scope

1. **Batch offers, approval, and subset selection** (FR-005, FR-006, FR-007, API-003, API-004): Extend SESSION_OFFER to carry multiple files with paths/sizes/hashes. Receiver validates all paths, checks destinations (existing-file policy, path containment, duplicate paths), presents the batch for operator approval, and returns SESSION_ACCEPT with the accepted file_ids subset. Rejected files produce per-file rejection reasons. No content transfers for rejected files.

2. **Paged manifest and transfer plan** (API-005, API-006): Send multi-file manifest via MANIFEST_BEGIN/PART/END pages. Receiver reassembles, validates digest and all file/chunk invariants, persists the accepted reference graph transactionally. Receiver then computes the exact missing-chunk set by joining manifest references against the verified store (cross-file and cross-transfer deduplication), and sends paged TRANSFER_PLAN with only truly missing hashes.

3. **Local cross-transfer deduplication** (FR-009, FR-016): When the receiver already holds a verified chunk from a prior transfer, it is not requested again. Unchanged re-transfer of the same files sends zero chunk payload. Edited re-transfer sends only the chunks whose hashes differ. The store's reference counting correctly tracks chunks shared across transfers.

4. **Partial result semantics** (API-011, FR-007): Individual files complete independently. FILE_RESULT reports success/failure per file. A batch is not transactionally atomic — completed files are not rolled back because another file fails. SESSION_RESULT aggregates per-state file counts. Partial success is a valid outcome with clear per-file status.

5. **Path reservation and destination conflict rejection** (FR-007, concurrency rules in 04_02): Multiple concurrent sessions cannot finalize the same relative path. The later conflicting offer is rejected (v1 policy). Path reservation is established at offer acceptance and released on completion/failure/cancellation.

6. **Idempotent retry and connection restart** (FR-018, failure matrix): Control connection loss triggers reconnect within budget. Data connection loss retries unacknowledged chunks. Duplicate CHUNK_PUT for already-verified hash returns ALREADY_PRESENT. Retry budgets count across reconnections for one session.

7. **Session resume with new capability** (API-009, FR-018, resume flow in 04_02): After sender/receiver restart, sender sends RESUME_REQUEST with transfer_id and manifest_digest. Receiver loads immutable session state, reconciles verified receipts, and returns RESUME_ACCEPT with a new session_capability and current missing hashes — or RESUME_REJECT with stable reason. Resume never trusts sender-reported progress. The new capability replaces the prior one; the old one is invalidated. Resume requires same peer, same manifest, compatible protocol. Representation/codec may change on retry.

8. **Concurrent session coordination** (concurrency rules in 04_02): Session state mutations are serialized. Destination path reservation prevents conflicts. Concurrent sessions remain fair and bounded within negotiated limits. kMaxConcurrentSessions (currently 4) is enforced.
