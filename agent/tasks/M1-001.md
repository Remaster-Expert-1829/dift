## Objective

Deliver the complete M1 offline engine from `docs/19_planning/19_01_milestones.md`: select multiple regular files safely, construct deterministic versioned manifests from content-defined chunks, store and reuse verified chunks durably, reconstruct byte-identical files, recover conservatively after interruption, and inspect/garbage-collect only proven-unreferenced data. This milestone has no network transfer.

The approved documentation corpus in `docs/README.md` is authoritative. Read the charter, requirements and user flows, ADR-002/004/007, system/components architecture, both `docs/05_data/` documents, internal component contracts, security/path rules, failure/recovery policy, test strategy, benchmark methodology's CDC evaluation, engineering standards, development and coding-agent workflows, milestones, Definition of Done, consistency review, and implementation readiness review.

## Scope

1. Deterministically select multiple files and recursively selected directories, normalize relative UTF-8/NFC manifest paths, reject duplicate/unsafe paths, and never follow symlinks. Use descriptor-relative containment for destination operations where applicable.
2. Implement streaming, bounded, deterministic Rabin content-defined chunking under an explicit parameterized profile, SHA-256 chunk and whole-file hashing, and source-change detection appropriate to offline manifesting.
3. Build and validate schema-1 canonical CBOR manifests with deterministic field/file/chunk ordering, explicit profile parameters, whole-file and chunk hashes, and a digest over the exact canonical bytes. Treat informational fields such as creation time as explicit inputs when testing determinism. Reject malformed or non-canonical forms within tested limits.
4. Implement SQLite schema versioning/migration and the content-addressed plaintext chunk store according to ADR-004 and `docs/05_data/`. Keep payloads outside SQLite. Preserve reference, lease, and verified-blob invariants.
5. Implement durable chunk installation, startup reconciliation, corruption quarantine, same-filesystem staging, whole-file verification, atomic finalization, store inspection, dry-run GC, and safe GC execution. Never finalize incomplete or corrupt data. Missing/invalid retention policy must retain data and report the condition.
6. Provide an offline tool or test harness that manifests a multi-file corpus, ingests and reuses chunks, reconstructs files, exercises recovery and GC, and produces reproducible correctness evidence without adding send/receive networking commands.
7. Run `EXP-CDC-001` on a declared corpus, record raw measurements and selection rationale, then freeze the `rabin-v1` polynomial/window/min/target/max profile with cross-build golden vectors. Keep the implementation parameterized before and after this selection.
8. Add pinned and licensed M1 dependencies through the existing build mechanism; update CI/tests and the approved documentation for profile/defaults, golden vectors, initial schema SQL/migration, filesystem durability assumptions, storage/path limits, traceability, risks, and readiness.

## Acceptance evidence

1. On the documented Linux baseline, a clean checkout can build and run the offline harness and M1 test suite under the existing GCC/Clang and sanitizer quality gates. M0 checks remain green.
2. File selection produces deterministic normalized paths for regular files; traversal, duplicates, invalid encodings, unsupported types, and symlink/race cases fail safely under the documented rules.
3. For arbitrary valid profiles and byte strings, chunks are deterministic, contiguous, bounded, and exactly reconstruct the input (`TEST-PROP-001`). Empty files have no chunk rows. SHA-256 and canonical CBOR have published/golden and negative fixtures.
4. Given the same explicit manifest fields, canonical bytes and digest are identical across repeated runs and supported compilers. Changed content, path, order, profile, or digest changes manifest identity as specified.
5. Two files/manifests referencing the same verified chunk reuse one payload. Reference counts match recomputed references, leases protect readers, and GC never selects referenced or leased chunks (`TEST-PROP-002`, relevant `TEST-INT-007/009`).
6. Fault injection around temporary write, flush, rename, SQLite commit, staging, final rename, disk-full, permissions, and corrupt/missing blobs establishes safe reconciliation. No unverified chunk is treated as present, no partial final file appears, and previous destinations survive failed replacement (`TEST-FAULT-002/003/004/006`).
7. Store inspection and GC dry-run make no changes. Actual GC removes only eligible, unreferenced, unleased data after the selected explicit policy and survives interruption.
8. `EXP-CDC-001` records the corpus, candidate profiles, chunk distribution, metadata count, reuse under edits, CPU/memory, and frame-compatibility analysis. The selected `rabin-v1` profile and golden vectors are committed with rationale; no unmeasured speed or bandwidth claim is presented as fact.
9. Schema-1 SQL, migration/rollback or recovery behavior, dependency versions/licenses, operational limits, and documentation are synchronized. An independent Reviewer inspects the actual diff and repository state and returns PASS for M1-001.
