## Format, schema, and data-flow boundaries

1. The offline flow is: selected regular files -> validated normalized paths -> bounded streaming CDC and chunk/whole-file SHA-256 -> canonical schema-1 CBOR and digest -> one-transaction accepted reference graph -> verified durable plaintext blobs and receipts -> leased ordered reconstruction -> whole-file size/hash verification -> same-filesystem atomic finalization. Inspection and GC read the same authoritative metadata/store.
2. Canonical manifest schema 1 uses the field labels and types shown in docs/05_data/05_01_manifest_and_chunk_store.md as literal lowercase ASCII CBOR map keys; no undocumented abbreviations or aliases are introduced. Before committing schema-1 golden bytes, update that document and the wire contract to list the exact keys, nested profile-parameter keys, integer ranges, and rejection policy. Preserve the approved field set, deterministic RFC 8949 ordering, sorted normalized file paths, file IDs assigned after sorting, ordered contiguous chunk references, explicit created_at_unix_ms, and digest over exact canonical bytes. Input selection order alone must not change canonical bytes; changed canonical file/chunk order or explicit field values must. Unknown schema, duplicate keys, noncanonical integers/map ordering, indefinite items, forbidden types, invalid UTF-8/NFC, extra/unknown required fields, and size/count excess fail before persistence.
3. SQLite schema 1 implements DB-000 through DB-007 in a checked, versioned 0-to-1 migration with stored content checksum and an interruption test. Enable/verify WAL and foreign keys per connection; use prepared statements, checked conversion to signed 64-bit integers, short write transactions, and a single-instance state-root lock. Unknown/newer schema never mutates. The accepted receiver graph (session, accepted files, catalog placeholders, ordered refs, session-chunk state, cached refcounts) commits atomically. Empty files have no chunk rows. Rejected file summaries may remain but acquire no refs. Refcounts are cached and recomputable, never sole GC proof.
4. The chunk store derives chunks/aa/bb/<lowercase-hash> only from a verified SHA-256 value. It verifies plaintext length/hash, detects HASH_METADATA_CONFLICT, writes a store-local unpredictable temporary name, flushes the file, atomically installs, flushes affected directories under the documented Linux durability model, then commits the catalog/receipt transaction. Only after all durable steps does the local commit operation return success; M2 may map that success to an ACK. Duplicate valid chunks are idempotent. Blob-without-row and row-without-valid-blob are repaired or quarantined conservatively at startup; missing/corrupt blobs invalidate dependent receipts.
5. Destination operations validate a normalized relative path below an opened root with descriptor-relative no-follow operations, including parent traversal and staging/finalization. Stage on the destination filesystem with exclusive creation and restrictive permissions; read only verified chunks under leases, verify the final size and whole-file SHA-256, flush staged bytes, atomically rename/replace only under explicit destination policy, and flush the final parent directory. A verified staging type/token gates finalize. No existing destination is modified before the final atomic operation.
6. GC has inspect, dry-run, and execute paths. Dry-run is read-only. Execute requires a validated explicit retention/grace policy; absent/invalid policy retains data and reports why. A short transaction recomputes refs and claims eligible unreferenced, unleased chunks with a GC lease; insertion of a new reference must observe the claim and wait/retry. Blob movement/deletion is outside the transaction; a second transaction rechecks claims/refs/leases before row removal. Active/read leases block deletion. A crash at any phase is reconciled without deleting uncertain data.
7. M1 must choose and document explicit offline limits for normalized path/segment bytes, selected file count, per-file and total chunk-reference count, canonical manifest bytes/depth, profile min/target/max, source/store/staging temporary bytes, reconciliation work, SQLite busy wait, and lease lifetime. Validate limits before allocation or SQLite narrowing, with boundary/over-limit tests and a resource rationale. These are M1 local safety limits; they do not close M2 network parser, handshake, or negotiated frame ceilings. The eventual rabin-v1 maximum must be compatible with the one-chunk-per-frame protocol rule before freeze.

## Compatibility, migration, security, and failure considerations

Schema 1 and its migration become the first persistent compatibility contract. Store exact canonical manifest bytes and schema/profile version. A future schema/profile change gets a new version or ID and tested migration; it cannot reinterpret old bytes. The 0-to-1 migration must be transactional where SQLite permits and refuse unknown/newer versions. Do not claim downgrade support beyond what is tested. SQLite WAL backup/restore needs the documented safe backup or stopped-process copy, not a main-DB-only copy.

M1 trusts local test fixture identity only inside the offline harness; it must not add a normal unauthenticated peer/transfer path. The local filesystem, input paths, decoded CBOR, and stored metadata still cross validation boundaries. Bound all counts/lengths and avoid using untrusted path strings as SQL, shell, or chunk-store names. Preserve plaintext-at-rest limitation. Never log source content, private keys, full sensitive roots, or fixture markers. Disk-full, permission failure, SQLite busy/corrupt, source mutation, invalid profile, and storage corruption must yield stable local errors without false success. Failed mandatory integrity checks enter inspect/read-only recovery rather than recreating the store. Missing/invalid retention policy retains chunks and reports the condition. No network, remote ACK, resume handshake, compression, scheduling, dashboard, or transfer speed claim is included.
